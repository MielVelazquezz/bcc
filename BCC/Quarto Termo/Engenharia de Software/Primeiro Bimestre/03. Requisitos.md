## <mark style="background: #FFB8EBA6;">O que é</mark>
- **Requisito** (IEEE Std 610.12, 1990): uma <mark style="background: #CACFD9A6;">condição ou capacidade</mark> que um sistema (ou componente) precisa satisfazer/possuir para atender um contrato, padrão ou especificação.
- **Especificação** (Aurélio, 1986): uma <mark style="background: #CACFD9A6;">descrição rigorosa e minuciosa</mark> das características que um material, obra ou serviço deve apresentar.

***Requisito é "o que precisa ser satisfeito"; especificação é "como isso fica descrito com detalhe e rigor".***

---

## <mark style="background: #FFB8EBA6;">Tipos de Requisitos: visão de Leite (1994)</mark>
Classificação mais simples/inicial:
- **Funcionais**: ligados direto à funcionalidade do software (o que ele faz).
- **Não funcionais**: aspectos de qualidade ou restrições que o software deve atender (como ele faz / sob que condições).
- **Inversos**: condições que **nunca poderão ocorrer**. (Ex.: "o sistema nunca deve permitir saldo negativo sem autorização")

---
## <mark style="background: #FFB8EBA6;">Tipos de Requisitos: visão de Sommerville (2003)</mark>
Voltada para **quem lê o documento** (nível de detalhe):
1. **Requisitos do usuário**: linguagem natural ou diagramas, para clientes e usuários. Falam das funções e restrições em alto nível (funcionais e não funcionais).
2. **Requisitos de sistema**: versão mais detalhada dos do usuário. Servem como **contrato** e são o ponto de partida do projeto do sistema.
3. **Especificação de projeto de software**: descrição abstrata do projeto, escrita para **desenvolvedores**. Base para projeto e implementação.

**Exemplo:**
- ***<mark style="background: #CACFD9A6;">Requisito do usuário</mark>***: "O software deve oferecer um meio de representar e acessar arquivos externos criados por outras ferramentas."
- ***<mark style="background: #CACFD9A6;">Requisitos de sistema</mark>***: definir o tipo do arquivo externo, associar uma ferramenta a cada tipo, representar por um ícone, ativar a ferramenta ao selecionar o arquivo.

**1 requisito de usuário pode virar vários requisitos de sistema quando se detalha.**

---

## <mark style="background: #FFB8EBA6;">Classificação dos Requisitos de Sistema (Sommerville, 2003)</mark> 
São **3 classes**: funcionais, não funcionais e de domínio.

---
## <mark style="background: #FFB8EBA6;">1. Requisitos Funcionais (RF)</mark>
Declarações de <mark style="background: #CACFD9A6;">funções que o sistema deve fornecer</mark>: como reage a entradas específicas e como se comporta em certas situações. Às vezes <mark style="background: #CACFD9A6;">também dizem o que o sistema NÃO deve fazer</mark>.

Podem envolver: cálculos, detalhes técnicos, manipulação de dados/processamento e outras funcionalidades específicas.

**Exemplos:**
- O usuário deve poder pesquisar em todo o banco de dados ou selecionar um subconjunto.
- O sistema deve armazenar RG, CPF, nome, data de nascimento e endereço do cliente.
- O sistema deve atribuir um identificador único (código) para cada pedido.
- O sistema deve cancelar automaticamente um orçamento com mais de 30 dias sem virar venda.

**A especificação de RF precisa ser:**
- **Completa**: todas as funções pedidas pelo usuário estão definidas.
- **Consistente**: sem definições contraditórias.

>[!question] Importante!
>A dificuldade de ser completo e consistente vem da complexidade do sistema + necessidades conflitantes de diferentes pontos de vista (cliente A quer uma coisa, cliente B quer outra).
>
>Um termo vago como "telas apropriadas" pode ser entendido diferente pelo usuário (uma tela específica para cada tipo de documento) e pelo desenvolvedor (uma tela genérica de texto). → **escreva o requisito de forma não ambígua**.

#### <mark style="background: #FFF3A3A6;">Tipos de requisito funcional: básica, fundamental e de saída</mark>
Na aula de documento de requisitos (IEEE 830), as **funções do produto** são divididas em 3 grupos:

| Tipo | O que é | Exemplos |
| --- | --- | --- |
| **Básica** | Operações **CRUD** (create, read, update, delete) necessárias para executar as funções fundamentais. O conjunto costuma ser chamado de **"Gerenciar"** | Gerenciar clientes, fornecedores, produtos |
| **Fundamental** | **Transações de negócio (movimentações)**. Agregam valor ao negócio; é o que o cliente aceita pagar e o motivo de a organização existir | Orçamento, venda, pedido de produção, contas a receber |
| **De saída** | Geram **informações de saída** relevantes: consultas/relatórios **com cruzamento de informações** (definem-se filtros de entrada e itens de saída) | Relatório de vendas por vendedor, extrato de contas |

- **Identificador:** `RF_B1`, `RF_F1`, `RF_S1` (B = básica, F = fundamental, S = saída).
- **Visibilidade:** cada função é **evidente** (visível ao usuário) ou **oculta** (imperceptível).

***Truque: cadastro = básica. Movimenta o negócio = fundamental. Relatório/consulta cruzando dados = saída.***

---
## <mark style="background: #FFB8EBA6;">2. Requisitos Não Funcionais (RNF)</mark>
São <mark style="background: #CACFD9A6;">restrições</mark> sobre os serviços/funções do sistema. Não dizem "o que" o sistema faz, dizem "como" ele deve se comportar ou que limites tem (tempo, processo de desenvolvimento, padrões etc.).

Na ERS aparecem como **atributos** (ex.: tolerância a falhas, tempo de resposta, portabilidade, segurança), com categoria **obrigatório** ou **desejável**.

#### <mark style="background: #FFF3A3A6;">RNF em 3 grupos (Sommerville)</mark>

| Grupo | De onde vem | Tipos e exemplos |
| --- | --- | --- |
| **Requisitos do produto** | Como o produto entregue deve se comportar | **Facilidade de uso** (operar após X tempo de treinamento); **Eficiência**: desempenho e espaço (processar *n* requisições em certo tempo); **Confiabilidade** (99% de disponibilidade); **Portabilidade** (rodar em qualquer plataforma) |
| **Requisitos organizacionais** | Políticas e procedimentos da própria empresa | **Entrega** (relatório toda segunda-feira); **Implementação** (desenvolver em Java); **Padrões** (POO na plataforma A) |
| **Requisitos externos** | Fatores de fora do sistema e do processo de desenvolvimento | **Interoperabilidade** (comunicar com SQL Server); **Éticos** (não mostrar dados privativos); **Legais** (seguir normas e leis; **privacidade** e **segurança** aparecem ligados aos legais na árvore da aula) |

Outro tipo citado: **Integração** (o sistema se conecta com outra aplicação).

---
## <mark style="background: #FFB8EBA6;">3. Requisitos de Domínio</mark>
Vêm **do domínio de aplicação** do sistema, não de um pedido direto do usuário. Podem ser **funcionais ou não funcionais**.

- Podem criar novos RF, restringir os existentes ou definir **como cálculos específicos** devem ser feitos.
- São importantes porque carregam o <mark style="background: #CACFD9A6;">conhecimento de negócio</mark> da área.
- **Exemplo (biblioteca):** "Deve haver uma interface-padrão com o usuário para todos os bancos de dados, baseada no padrão Z39.50". É uma restrição sobre uma exigência funcional.
- **Dificuldade**: usam linguagem própria do domínio, que o analista muitas vezes não domina (ex.: termos de Departamento de Pessoal ou de plano de saúde). Só quem trabalha há anos na área conhece bem.

---
## <mark style="background: #FFB8EBA6;">Funcional x Não funcional: a fronteira não é tão clara</mark>
Um requisito de usuário sobre **proteção/segurança** parece não funcional. Quando detalhado, pode gerar requisitos **claramente funcionais**, como incluir recursos de **autorização de usuários** no sistema.

**Regra prática:**
- Descreve uma **função/ação** do sistema? → **Funcional** (e decida: básica, fundamental ou saída)
- Descreve **tempo, disponibilidade, linguagem, plataforma, lei, padrão, ética ou qualidade**? → **Não funcional**
- Tem **número ou métrica** (segundos, %, nº de usuários)? → quase sempre **não funcional**

---
## <mark style="background: #FFB8EBA6;">Treino para a prova</mark>
1. "O sistema deve armazenar nome, CPF e endereço dos clientes." → **RF básica**
2. "O sistema deve cancelar automaticamente orçamentos com mais de 30 dias sem venda." → **RF fundamental**
3. "O sistema deve gerar relatório de vendas por vendedor." → **RF de saída**
4. "O sistema deverá ter disponibilidade de 99% do tempo." → **RNF (confiabilidade)**
5. "O sistema deverá ser desenvolvido em Java." → **RNF (implementação, organizacional)**
6. "O sistema deverá se comunicar com o SQL Server." → **RNF (interoperabilidade, externo)**
7. "O sistema não apresentará dados de cunho privativo aos usuários." → **RNF (ético, externo)**
8. "Um relatório de acompanhamento deverá ser fornecido toda segunda-feira." → **RNF (entrega, organizacional)**
