## <mark style="background: #FFB8EBA6;">O que é o modelo de casos de uso</mark>
Serve para:
- **delimitar o sistema e seu ambiente**
- ser **base de acordo** entre as partes
- **acompanhar o progresso** do trabalho

**É composto por:** diagrama de casos de uso + especificação de casos de uso + diagrama de atividades dos casos de uso.

> [!note] Ele nasce incompleto
> No início do levantamento ainda não se conhecem todos os requisitos. Por isso o modelo é definido **junto com o escopo**, durante a coleta de requisitos.

---
## <mark style="background: #FFB8EBA6;">Casos de uso e atores</mark>

#### <mark style="background: #FFF3A3A6;">Caso de uso</mark>
- **Modela requisitos funcionais** e serve de acordo entre as partes
- Descreve o comportamento do sistema conforme as requisições dos atores, sob diversas condições
- Deve ser **fácil de ler**, entendível sem conhecer a área; mostra a visão do usuário realizando suas tarefas
- Na UML é uma **elipse**
- O nome representa a **visão do sistema** e começa com **verbo no infinitivo**. Ex.: o cliente "compra no balcão", mas para o sistema o caso de uso é **"Vender produtos"**

#### <mark style="background: #FFF3A3A6;">Ator</mark>
- Quem **inicia** o caso de uso: pessoas que operam o sistema, ou **outros sistemas e hardwares**
- Na UML é um **"boneco de palito"**
- Se o cliente fala com o funcionário e o funcionário usa o sistema, o **ator é o funcionário**

> [!warning] Cai em prova
> O modelo de casos de uso **não apresenta as funções básicas e de saída** (RF_B e RF_S). Documenta **apenas as fundamentais (RF_F)**.
> Um caso de uso deve representar um **resultado significativo que o cliente aceita pagar** e realizar **uma função específica, nem mais nem menos do que o necessário**.

---
## <mark style="background: #FFB8EBA6;">Fases para montar o modelo</mark>
1. **Encontrar atores e casos de uso** (delimitar o sistema; mostrar quem interage com o quê)
2. **Definir o glossário** de termos comuns
3. **Detalhar** os casos de uso (fluxo de eventos)
4. **Definir prioridades** (ordem de desenvolvimento e dependências entre casos de uso)

#### <mark style="background: #FFF3A3A6;">Como encontrar casos de uso e atores</mark>
- **Método baseado em atores:** identifique os atores e, para cada um, os processos de que participa. Perguntas úteis: quais grupos de usuários precisam do sistema para suas tarefas? Quais são necessários para as funções principais? O sistema interage com algum equipamento ou outro sistema? Depois: o que o ator espera que o sistema faça e o que o sistema oferece a ele.
- **Método baseado em eventos:** identifique os eventos aos quais o sistema deve responder e relacione-os aos atores. Pergunte: quais as responsabilidades do sistema? Em quais processos o ator atinge um objetivo de negócio? Como o ator usa os serviços do sistema?

## <mark style="background: #FFB8EBA6;">Relacionamentos</mark>

| Entre                         | Tipo                             | Significado                                                                                               |
| ----------------------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Ator e caso de uso**        | **Associação simples**           | Participação do ator no caso de uso (troca de informação). Com seta, mostra **quem inicia** a comunicação |
| **Ator e ator**               | **Generalização/especialização** | O ator filho **herda** comportamento e atributos do pai                                                   |
| **Caso de uso e caso de uso** | **Generalização/especialização** | O caso de uso filho herda o comportamento do pai                                                          |
| **Caso de uso e caso de uso** | **`<<include>>`** (inclusão)     | A **inclui** o comportamento de B. Facilita **reutilização**; cuidado para não gerar quebra funcional     |
| **Caso de uso e caso de uso** | **`<<extend>>`** (extensão)      | Parte **opcional** ou executada só sob certas **condições/exceções**                                      |

*(Estereótipo: mecanismo usado para ampliar a UML, como `<<include>>` e `<<extend>>`.)*

> [!tip] Include x Extend
> **Include** = sempre acontece (comportamento obrigatório reaproveitado). **Extend** = só acontece às vezes (opcional ou exceção).

## <mark style="background: #FFB8EBA6;">Especificação de casos de uso</mark>
Feita **para cada caso de uso**. Descreve os serviços usados pelo ator e como ele os realiza, mostrando o **fluxo alternado ator ↔ sistema**.

**Modelo simplificado:** Caso de uso, Atores, Descrição.

**Modelo estendido (campos do exemplo):** Caso de uso · Referências (ex.: `RF_F1`) · Descrição geral · Atores · **Pré-condições** · **Garantia de sucesso (pós-condições)** · Requisitos especiais · **Fluxo básico** · **Fluxos alternativos**

#### <mark style="background: #FFF3A3A6;">Como escrever o fluxo</mark>
1. Pense primeiro no **cenário básico sem o sistema** (só a interação de negócio cliente x vendedor), com tudo dando certo
2. Depois reescreva com a **interação ator x sistema** (ainda só o caminho feliz)
3. Por fim, para **cada passo** do fluxo normal, pense em **eventualidades** e em **como o sistema reage** (fluxos alternativos)

#### <mark style="background: #FFF3A3A6;">Exemplo: Vender produtos no balcão (RF_F1)</mark>
- **Ator:** Vendedor
- **Pré-condições:** cliente cadastrado; produto cadastrado e disponível em estoque
- **Pós-condições:** venda registrada, recebimento registrado, nota fiscal emitida, estoque atualizado
- **Requisito especial:** tolerância a falhas por transação em banco de dados

**Fluxo básico:**
1. Vendedor informa o CPF do cliente
2. Sistema pesquisa o cliente e inicia a venda
3. Vendedor informa o produto (código de barras) e a quantidade
4. Sistema verifica e registra o item (descrição, preço unitário, preço total)
5. Repete 3 e 4 até o vendedor indicar que terminou
6. Sistema informa o total e lista as formas de pagamento
7. Vendedor seleciona a forma de pagamento
8. Sistema registra o pagamento, emite a nota fiscal, atualiza o estoque e finaliza

**Fluxos alternativos:**
- **2.1** Cliente não cadastrado → sistema avisa e finaliza o caso de uso
- **4.1** Dados do produto inválidos → sistema avisa e permite informar outro produto
- **4.2** Quantidade indisponível em estoque → sistema informa a quantidade atual e permite nova quantidade ou novo produto
