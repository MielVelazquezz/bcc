## <mark style="background: #FFB8EBA6;">O que é a ERS</mark>
**ERS** (ou **SRS**, Software Requirements Specification) é o documento de **Especificação de Requisitos de Software**. A norma **IEEE Std 830/1998** recomenda como escrevê-lo. (IEEE = Institute of Electrical and Electronics Engineers.)

A ERS:
- permite ao **cliente descrever** suas necessidades e ao **desenvolvedor compreendê-las**
- define **todos os requisitos** que devem compor o software
- é a **base do acordo** entre clientes e desenvolvedores sobre o que o software fará

Existem outras estruturas (ex.: Sommerville, Turine). A do IEEE 830 é genérica e deve ser **instanciada** para cada sistema.

---
## <mark style="background: #FFB8EBA6;">Para produzir uma boa ERS</mark>

#### <mark style="background: #FFF3A3A6;">Natureza: 5 questões básicas</mark>
- **Funcionalidade:** o que o software pretende fazer?
- **Interfaces externas:** como interage com pessoas, hardware e outros softwares?
- **Performance:** velocidade, disponibilidade, tempo de resposta e de recuperação
- **Atributos:** portabilidade, manutenibilidade, segurança, corretitude etc.
- **Restrições de implementação:** padrões, linguagem, integridade do BD, limites de recursos, ambiente operacional

#### <mark style="background: #FFF3A3A6;">Ambiente</mark>
A ERS deve estar de acordo com os requisitos do sistema, definir corretamente os requisitos de software, **não descrever detalhes de projeto ou implementação** e não criar restrições adicionais (estas ficam em outros documentos, como o plano de garantia de qualidade).

#### <mark style="background: #FFF3A3A6;">Características de uma boa ERS</mark>

| Característica | Significa |
| --- | --- |
| **Correta** | Cada requisito da ERS é encontrado no software |
| **Não ambígua** | Cada requisito tem **uma só interpretação** |
| **Completa** | Inclui todos os requisitos significativos (funcionalidade, desempenho, restrições), respostas para todas as entradas e saídas, e nomes/referências de tabelas, figuras, diagramas, termos e unidades |
| **Consistente** | Sem conflito entre requisitos |
| **Com grau de importância/estabilidade** | Cada requisito indica sua importância (essencial, condicional, opcional) ou estabilidade (quantas mudanças se esperam) |
| **Verificável** | Dá para checar cada requisito; usam-se termos concretos e quantidades mensuráveis |
| **Modificável** | Fácil de alterar de forma consistente: organização coerente, índice e referência cruzada, **sem redundância**, cada requisito expresso **separadamente** |
| **Rastreável** | A origem de cada requisito é clara e ele pode ser referenciado no desenvolvimento futuro |

#### <mark style="background: #FFF3A3A6;">Preparação</mark>
- Cliente e fornecedor **trabalham juntos** para produzir uma ERS bem escrita e completa
- A ERS pode ser elaborada **durante** o desenvolvimento
- Um **protótipo** pode ser usado para levantar requisitos

## <mark style="background: #FFB8EBA6;">Estrutura da ERS</mark>
A versão adotada nas aulas da Unoeste:

1. **Introdução**
   - 1.1 Objetivo · 1.2 Escopo · 1.3 Definições, siglas e abreviações · 1.4 Referências · 1.5 Informações adicionais (dados da instituição, da empresa, legislação de software) · 1.6 Visão geral
2. **Descrição geral do produto**
   - 2.1 Estudo de viabilidade (2.1.1 justificativa da alternativa selecionada) · 2.2 **Funções do produto** · 2.3 Características do usuário · 2.4 Limites, suposições e dependências · 2.5 Requisitos adiados
3. **Requisitos específicos** (todos os requisitos com detalhe suficiente para projetar o sistema; em APOO são detalhados)

> [!note] Versão do IEEE original
> No slide da norma, a seção 2 aparece como: 2.1 Perspectiva do produto, 2.2 Funções do produto, 2.3 Características do usuário, 2.4 Restrições, 2.5 Suposições e dependências, 2.6 Requisitos adiados. Siga a estrutura que seu professor pedir.

#### <mark style="background: #FFF3A3A6;">O que vai em cada parte da Introdução</mark>
- **Objetivo:** delinear o objetivo da ERS e o **público-alvo** (cliente, analista, desenvolvedor)
- **Escopo:** texto que descreve o produto e as funcionalidades necessárias ao processo de negócio; identifica o produto pelo nome; diz **o que fará e, se preciso, o que não fará** (ex.: "nesta fase não será desenvolvido o comércio eletrônico")
- **Definições, siglas e abreviações:** termos necessários para entender a ERS (ex.: *Backup: cópia de segurança dos dados*)
- **Referências:** lista de documentos citados, com título, número, data e quem forneceu (ficam em anexo)
- **Visão geral:** o que conterá a ERS e como está organizada

## <mark style="background: #FFB8EBA6;">Seção 2: Descrição geral do produto</mark>
Descreve **fatores gerais** e dá o contexto, mas **não** traz os requisitos específicos (esses ficam na seção 3).

- **2.1 Estudo de viabilidade:** alternativa de informatização escolhida, considerando viabilidade **técnica, econômica e legal**, com vantagens/desvantagens (custo x benefício). As alternativas **rejeitadas** vão em apêndice (identificação, análise de custos, benefícios).
- **2.2 Funções do produto:** **a parte mais importante da seção.** Lista as funções **básicas, fundamentais e de saída** (veja `03. Requisitos`).
- **2.3 Características do usuário:** nível educacional, experiência e conhecimento de informática, para saber se precisa de **treinamento**.
- **2.4 Limites, suposições e dependências:** o que limita o desenvolvedor (normas, hardware, memória, interfaces, linguagem, protocolos, segurança). *Exemplo:* o limite é não comprar o ponto eletrônico; a suposição é que ele será comprado; sem ele, a entrada de dados seria manual.
- **2.5 Requisitos adiados:** requisitos que ficam para versões futuras.

#### <mark style="background: #FFF3A3A6;">Tabelas da seção 2.2</mark>

**Tabela de funções**

| Coluna | Descrição |
| --- | --- |
| **Referência** | Identificador para rastreabilidade: `RF_B1` (básica), `RF_F1` (fundamental), `RF_S1` (saída externa) |
| **Função** | Nome da função, sem detalhamento |
| **Visibilidade** | **Evidente** (visível ao usuário) ou **oculta** (imperceptível) |

**Tabela de atributos (requisitos não funcionais)**

| Coluna                    | Descrição                                                                                                                         |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Atributo**              | Característica que afeta todas as funções ou uma específica (tolerância a falhas, tempo de resposta, portabilidade, segurança...) |
| **Detalhes e restrições** | Descreve o atributo em detalhes                                                                                                   |
| **Categoria**             | **Obrigatório** ou **desejável**                                                                                                  |

Observação: funções de gerenciamento de usuário, backup e restauração não entram aqui, pois já são descritas em "Perspectiva do produto".
