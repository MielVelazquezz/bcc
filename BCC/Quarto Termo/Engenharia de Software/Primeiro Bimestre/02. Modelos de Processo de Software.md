Um **modelo de processo** descreve, de forma organizada, as atividades para obter um software com segurança. Também é chamado de **paradigma** ou **modelo de ciclo de vida**. Cada modelo é uma tentativa de organizar uma atividade que é naturalmente caótica.

**Escolha do modelo depende de:** natureza do projeto/aplicação, métodos e ferramentas usados, controles e produtos a entregar.

**Modelos prescritivos tradicionais:** Cascata, Prototipação, Incremental e Espiral.

---
## <mark style="background: #FFB8EBA6;">Modelo Cascata (Sequencial Linear)</mark>
- O **mais antigo** e mais usado da engenharia de software
- Abordagem **sistemática e sequencial**, com foco em **documentos e artefatos**
- Cada etapa só começa quando a anterior termina

**Etapas:** Engenharia de Sistemas → Análise de Requisitos → Projeto → Codificação → Testes → Manutenção

| Etapa | O que acontece |
| --- | --- |
| **Engenharia de Sistemas** | Coleta de requisitos em **nível de sistema** |
| **Análise de Requisitos** | Coleta focada no **software**; requisitos documentados e revistos com o cliente |
| **Projeto** | Traduz os requisitos em representações avaliáveis **antes** de codificar: estrutura de dados, arquitetura, detalhes procedimentais, interfaces |
| **Codificação** | Traduz o projeto em instruções executáveis pelo computador |
| **Testes** | Aspectos **lógicos internos** (todas as instruções testadas) e **funcionais externos** (a entrada gera o resultado esperado) |
| **Manutenção** | Mudanças após a entrega (tipos abaixo) |

#### <mark style="background: #FFF3A3A6;">Tipos de manutenção</mark>
- **Corretiva** → corrige erros
- **Adaptativa** → adapta o software a mudanças de ambiente
- **Evolutiva** → acréscimos funcionais e de desempenho
- **Preditiva** → melhora a manutenibilidade (nome usado nos slides)

> [!warning] Problemas do Cascata
> - Projetos reais **raramente seguem** o fluxo sequencial
> - É difícil estabelecer **todos os requisitos no início** (sempre há incerteza)
> - O cliente precisa ter **paciência**: a versão executável só aparece numa etapa avançada

---
## <mark style="background: #FFB8EBA6;">Prototipação</mark>
- **Objetivo:** entender os requisitos do usuário, criando um **protótipo** do software
- Indicado quando o cliente definiu **objetivos gerais**, mas não os requisitos em detalhe

**Ciclo:** Obter requisitos → Elaborar projeto rápido → Construir protótipo → Avaliar protótipo → Refinar (e repete)

- **Obter requisitos:** desenvolvedor e cliente definem objetivos gerais, o que já é conhecido e o que precisa ser detalhado
- **Projeto rápido:** representa o que é **visível ao usuário** (formatos de entrada e saída)
- **Avaliação:** cliente e desenvolvedor avaliam e **refinam os requisitos**
- Com os requisitos claros, o protótipo é **descartado** e a versão de produção é construída com critérios de qualidade

> [!warning] Problemas
> - Qualidade global e manutenibilidade **não foram consideradas** no protótipo
> - Usa-se o que estiver disponível para fazer rápido (implementação comprometida)
> - **Chave:** combinar com o cliente, desde o início, que o protótipo serve só para **definir requisitos**

---
## <mark style="background: #FFB8EBA6;">Modelo Incremental</mark>
- Junta os benefícios do **Cascata** e da **Prototipação**
- Ideia: desenvolver (projeto, codificação e teste) o software **em incrementos**, priorizando as funcionalidades principais

**Ciclo:** Definir escopo dos requisitos → Priorizar requisitos (incrementos) → Projetar arquitetura → Desenvolver incremento → Integrar → Verificar e validar → Versões → Versão final

**Vantagens:**
- O cliente **não espera** a versão final para começar a usar
- Os primeiros incrementos servem como **protótipo** para refinar requisitos
- **Menor risco** de fracasso
- As funções prioritárias são entregues primeiro, então passam por **testes mais intensivos**

---
## <mark style="background: #FFB8EBA6;">Modelo Espiral</mark>
- Une o melhor do **Cascata** e da **Prototipação** e adiciona a **Análise de Risco**
- Usa protótipo em qualquer etapa como forma de **reduzir riscos**
- Dividido em **regiões de tarefa** (tipicamente de 3 a 6)
- **Cada volta (loop)** da espiral é uma fase do processo

**Versão com 4 regiões (quadrantes):**
1. Determinar **objetivos, alternativas e restrições**
2. Avaliar alternativas, **identificar e resolver riscos**
3. **Desenvolver e verificar** o produto no próximo nível
4. **Planejar** a próxima fase

**Voltas de exemplo (de dentro para fora):** viabilidade (concepção da operação) → requisitos do software → projeto do software → construção (código, testes).

**Versão com 6 regiões:** comunicação com o cliente, planejamento, análise de riscos, engenharia, construção e liberação, avaliação do cliente.

**Comentários:**
- **Não existem fases fixas**: a gerência decide como estruturar o projeto
- Permite ao desenvolvedor e ao cliente **entender e reagir aos riscos** a cada etapa
- Exige **muita experiência** na análise de riscos e depende dela para ter sucesso

---
## <mark style="background: #FFB8EBA6;">Comparação rápida</mark>

| Modelo | Ideia principal | Ponto forte | Ponto fraco |
| --- | --- | --- | --- |
| **Cascata** | Etapas em sequência | Simples, bem documentado | Rígido; requisitos todos no início; entrega tardia |
| **Prototipação** | Protótipo para descobrir requisitos | Esclarece requisitos vagos | Protótipo pode virar produto sem qualidade |
| **Incremental** | Entregas por partes | Uso antecipado, menor risco | Exige boa priorização e integração |
| **Espiral** | Voltas com análise de risco | Trata riscos a cada volta | Exige experiência em riscos |

## <mark style="background: #FFB8EBA6;">Processos prescritivos (visão geral)</mark>
- Buscam **aderência a normas e padrões**, com forte ênfase em **controles e documentação**
- Voltados para **equipes grandes e/ou dispersas**
- Atendem a várias exigências do **CMMI** e da **ISO**
- Costumam ser **personalizados** para cada projeto/empresa

**Exemplos:** Unified Process (UP/RUP) e variações (EUP), MSF (Microsoft Solutions Framework), ICONIX, Catalysis, OPEN.

#### <mark style="background: #FFF3A3A6;">UP (Unified Process)</mark>
UP é o RUP sem a marca registrada do produto Rational. Baseia-se em **3 princípios**:
1. **Dirigido por Use Cases (casos de uso):** cada interação de um tipo de usuário (ator) com o sistema
2. **Centrado em arquitetura:** as diferentes visões que formam a solução completa
3. **Iterativo e incremental:** o projeto é quebrado em "mini-projetos" chamados **iterações**

Uma iteração é uma sequência completa de disciplinas (workflow) e gera **artefatos** (código-fonte, modelo etc.).

**Fases do UP** (os slides descrevem o conteúdo de cada uma):

| Fase | O que se faz |
| --- | --- |
| **Concepção** | Define o escopo, avalia tecnologia, lista riscos principais, detecta áreas críticas, verifica a **viabilidade** |
| **Elaboração** | Especifica os requisitos em detalhe, identifica e avalia a **arquitetura** |
| **Construção** | Constrói o produto e testa versões beta |
| **Transição** | Testa a versão para entrega ao cliente e **implanta** o sistema |

#### <mark style="background: #FFF3A3A6;">EUP (Enterprise Unified Process)</mark>
Extensão do RUP. Acrescenta:
- **2 novas fases:** **Produção** (apoio à operação e suporte) e **Retirada** (tirar o sistema de operação; trocar sistemas legados com impacto mínimo no negócio)
- **Novas disciplinas:** modelagem do negócio da empresa, gestão de portfólio, arquitetura empresarial, reuso estratégico, gestão de pessoas, administração empresarial, melhoria do processo de software
